# 广东美食协同过滤推荐系统

> 基于 Python + Flask 的广东美食智能推荐系统毕业设计

## 项目简介

本系统是一个面向广东特色美食的智能推荐平台，实现 **User-CF 与 Item-CF 两套协同过滤算法**，并引入**偏置项（μ + b_u + b_i）与相似度收缩**改进预测精度；同时提供随机、热门两条基线用于对照实验。系统提供用户、商家、管理员三类角色，覆盖美食浏览、评分、点赞、收藏、评论、举报等完整交互，并内置离线评估模块（Precision@N / Recall@N / NDCG@N / 覆盖率 + MAE/RMSE），可在页面直接对比四种策略的效果。

## 技术栈

| 类别 | 技术 |
|------|------|
| 后端框架 | Python 3.11 + Flask 3.1 |
| 数据库 | MySQL 8.0 + PyMySQL |
| 推荐算法 | User-CF / Item-CF（皮尔逊相关 + 偏置项 + 相似度收缩），NumPy 实现 |
| 密码加密 | Werkzeug（`generate_password_hash`，scrypt） |
| 可视化 | ECharts 5.4（本地引入） |

## 核心功能

### 用户端
- 注册 / 登录 / 退出（含商家注册，密码加密存储）
- 首页浏览、关键词搜索（含粤菜同义词扩展）、分类筛选
- **首页每日热榜**：内嵌在头部右侧的卡片轮播（左侧仍是标题与搜索，两块共用一张背景图），按「当天浏览量 + 近 7 天新口碑」
  全站排序，所有人看到的是同一份，和「猜你喜欢」的个性化推荐是两条独立链路；支持自动播放、悬停暂停、
  卡片两侧隐藏箭头、底部缩略条（悬停即切换）、方向键和手机左右滑动；搜索/筛选时热榜收起，头部自动降级为纯搜索版式
- 美食详情、评分（1-5 星）、点赞、收藏、评论
- 浏览记录、个人中心（横幅 + 数据入口卡布局）、过敏/忌口设置、黑名单管理、我的举报、修改密码（折叠在「账号安全」里，点开才显示）
- 饮食偏好：含过敏/忌口的美食在首页标出提醒，可勾选「隐藏后不再推荐」（首页临时开关 + 个人中心持久化，推荐侧同步生效）
- 站内消息：按对话对象聚合的**会话列表 + 完整聊天记录页**（气泡对话、日期分隔、Enter 发送、自动定位最新一条），
  不再是拆开的"收到的 / 已发出"两堆；导航栏带未读数红点
- 全站统一的「返回」按钮（导航条左侧圆形箭头，首页不显示；优先走浏览器历史，从登录/注册页或外链进入则回首页）

### 商家端
- 商家注册（需管理员审核，审核通过前不能管理美食）
- 数据看板（ECharts 柱状图：本店美食评分 + 点赞排行）
- 美食上传（**支持上传图片**，自动裁剪压缩为 736×552）、编辑、下架、重新上架（需再审）

### 管理员端
- 数据看板（ECharts 饼图/柱状图/折线图 + 待处理举报入口）
- 商家审核、美食审核、用户管理（分页/搜索/角色筛选/禁用）
- 举报管理（处理弹窗，可**同步下架被举报美食 / 删除被举报评论**，并回填处理说明）
- 举报核实：被举报美食/评论可直接点开（下架、待审核的菜管理员也看得到，评论带锚点定位），并可**一键站内联系商家 / 评论者 / 举报人**，沟通记录留痕

### 推荐算法
- User-CF / Item-CF 双算法，皮尔逊相关（共现去均值）+ 偏置项 + 相似度收缩
- 冷启动（新用户评分不足时按**贝叶斯加权好评分**兜底：好评总分向先验收缩，
  并剔除「评分人数 ≥5 却平均分 <3.5」的菜，不把差评菜推给新用户）
- 过敏强制过滤、忌口主动标注、黑名单双维度过滤
- **可解释推荐**：每张推荐卡片展示「为什么推荐它」（基于 Item-CF 的相似菜品追溯）+ 预测评分 + 口味画像
- **可解释但不堆指标**：相似度不直接抛 0.xx 的数字给用户（容易被误读成"才 30%"），统一翻译成「非常接近 / 比较接近 / 有点接近」+ 星级
- **相似菜品**：详情页给出与当前菜品口味最接近的 4 道菜（同一批人一起打高分），并展示「本店其他美食」带缩略图
- **分批展示**：推荐页首屏 12 道，点「加载更多」每次再展开 12 道，单次最多算 48 道
  （越往后与用户口味的关联越弱，硬凑数量只会推出不相干的菜；无相似度支撑的新菜不硬推）
- 离线评估：按用户分层留出法（20%），Precision@N / Recall@N / NDCG@N / 覆盖率 + MAE/RMSE
- 对照组：随机推荐、热门推荐，评估页可直接对比四种策略与不同 K 值

## 数据库设计（12 张表）

| 表名 | 用途 |
|------|------|
| `users` | 用户（user / merchant / admin），含过敏、忌口、商家审核状态 |
| `categories` | 美食分类（12 类：肠粉/烧腊/早茶点心/粥品/粉面/煲仔饭/糖水甜品/广府菜/潮汕菜/客家菜/海鲜/饮品） |
| `foods` | 美食（价格、原材料、口味描述、审核状态等） |
| `ratings` | 评分（1-5 星，user_id + food_id 唯一） |
| `likes` | 点赞 |
| `favorites` | 收藏 |
| `comments` | 评论 |
| `histories` | 浏览记录（每用户每菜一条，记最后浏览时间） |
| `food_views` | 浏览明细（PV 口径，一次访问一条，供每日热榜统计；含匿名访客标识用于去重） |
| `blacklists` | 黑名单（支持美食 / 商家双维度） |
| `reports` | 举报（美食 / 评论，含管理员处理说明 `handle_note`） |
| `messages` | 站内消息（发送者、接收者、正文、关联举报、已读标记） |

> `histories` 与 `food_views` 口径不同、各司其职：前者是「我看过哪些菜」（去重，给用户自己看），
> 后者是「这道菜被看了多少次」（明细，给热榜算 PV）。

## 安全设计

| 风险 | 处置方式 |
|------|----------|
| 注册提权 | 角色走白名单 `('user','merchant')`，表单伪造 `role=admin` 会被强制降级为普通用户 |
| CSRF | 会话内随机令牌 + 全局 `before_request` 校验；表单带 `_csrf_token` 隐藏域，AJAX 统一走 `X-CSRFToken` 请求头（`base.html` 自动注入，业务代码零改动） |
| 会话固定 | 登录成功后 `session.clear()` 再写入身份 |
| 暴力破解 | 同 IP + 同用户名 5 分钟内错 5 次锁定 5 分钟（`utils/security.py`） |
| 越权访问 | 商家只能操作 `merchant_id = self` 的菜品；管理员接口逐个校验 `role == 'admin'` |
| 开放重定向 | 登录 `next` 参数只接受站内路径（`/` 开头且非 `//`） |
| 上传文件 | 校验真实图片格式（Pillow 解码）与 5MB 上限，统一重编码为 JPEG，文件名用 uuid，杜绝路径穿越与伪装脚本 |
| 强制下线 | `退出登录` 改 POST，避免 ` <img src="/logout"> ` 式攻击 |
| 信息泄露 | 数据库异常不再回显到页面/AJAX，统一提示「操作失败，请稍后重试」 |
| XSS | Jinja2 默认自动转义；管理端不再把菜名拼进 `onclick`，改用 `data-*` 属性 |

## 界面与视觉设计

界面统一走「岭南茶楼」的质感：陶土红 + 旧金 + 米白 + 炭墨，既有餐饮的暖意，又不至于像外卖 App 那样高饱和。所有页面的颜色、圆角、阴影、字号都来自同一套 CSS 变量，改一处即可全站生效。

样式分两层：

| 文件 | 职责 |
|------|------|
| `static/css/theme.css` | 设计变量（`--brand` / `--gold` / `--ink` / `--r` / `--sh-1` …）+ 通用组件：导航、按钮、卡片、表单、表格、徽章、美食卡片、空状态、页脚 |
| 各页面 `<style>` | 只写本页特有的布局（例如首页封面、详情页两栏、后台图表区），不再重复定义按钮和卡片 |

核心色板：

| 变量 | 色值 | 用途 |
|------|------|------|
| `--brand` | `#A23A25` | 主色：主按钮、价格、强调数字 |
| `--brand-dark` | `#7D2B1A` | 主色按下 / 悬停 |
| `--gold` | `#B98A3E` | 评分星标、次级强调、最优行高亮 |
| `--jade` | `#2F6B57` | 正向状态：通过、已处理、已读 |
| `--ink` | `#221C18` | 主文字（炭墨，比纯黑柔和） |
| `--paper` | `#FBF7F1` | 页面底色（米白，带两层极淡径向渐变） |
| `--line` | `rgba(34,28,24,.09)` | 分隔线 / 卡片描边 |

排版上：中文大标题用宋体（`--font-serif`）拉开与传统餐饮的关联，正文用系统无衬线保证小字清晰，数字统一走等宽字体（`--font-num`）并对齐，价格、评分、统计值不会跳动。

几个具体的处理：

- **导航**：深红渐变底 + 底部一条金色细线，logo 是方形印章，链接悬停时金色下划线从左展开；未读消息用金色数字气泡。
- **首页**：头部是一整块沉浸式横幅——左边大标题 + 简介 + 内嵌搜索框 + 热门词，右边是今日热榜卡片，两块压在同一张
  （轻度虚化压暗的）菜品照片上，中间不出现硬切的分界；搜索/筛选时热榜收起，头部缩成纯搜索版式。下面才是分类快筛和卡片流。
- **美食卡片**：图片固定 4:3、卡片整体等高，图片底部加一层极淡渐隐压住过亮的照片；评分用金色 ★，价格用主色等宽数字。
- **详情页**：左图右信息的杂志版式，评分分布从纯文字改为条形图；窄屏时评分/互动卡自动提到评论前面，不用滚到底才能打分。
- **图表**：ECharts 统一去掉默认高饱和配色，改为主色渐变柱 + 金色辅助线，坐标轴只保留浅色分割线。
- **图标**：全站不再使用 emoji，改用极简符号与 CSS 绘制，避免「随手拼出来」的观感。

响应式断点：`980px`（详情页转单列）、`900px`（后台图表转单列）、`768px`（导航收紧、卡片两列）、`480px`（极窄屏让位给功能入口）。

## 运行方式

### 1. 安装依赖

```bash
cd gd_food_recommend
pip install -r requirements.txt
```

### 2. 初始化数据库

不需要手动建库，`create_tables.py` 会自动创建 `food_db` 与 12 张表：

```bash
python create_tables.py        # 建库建表（可重复执行，不会清空数据）
python migrate_v2.py           # 已有库升级：补 users.hide_risk 字段与 messages 表（可重复执行）
python migrate_v3.py           # 已有库升级：补 food_views 浏览明细表并回填历史浏览（可重复执行）
python insert_data.py          # 可选：插入早期 10 道菜与演示账号
python seed_catalog.py         # 同步 12 个分类 / 15 个商家 / 74 道菜（幂等）
python generate_mock_data.py   # 生成 200 用户 + 5000 条评分（可复现）
python seed_behavior.py        # 由评分派生点赞 / 收藏 / 浏览（保证行为自洽，--seed 换一批）
python seed_comments.py        # 按菜品与评分重新生成模拟评论（文本按分类/菜名匹配，作者须评过该菜）
python seed_food_views.py      # 生成近两周浏览 PV 大盘（首页每日热榜要用；--reset 可清掉）
```

> **说明**：`generate_mock_data.py` 会先清空上一次生成的模拟数据再重新生成，保证结果可复现；
> 如需完全还原为真实小数据集，执行 `python generate_mock_data.py --purge`。
> 论文中的实验结果即基于该数据集（204 用户 / 74 菜品 / 5075 条评分，矩阵密度 33.6%）。
>
> **行为数据口径**：`seed_behavior.py` 让点赞、收藏、浏览都从评分派生——先浏览、再评分，
> 然后按分数概率决定是否点赞/收藏（5★ 点赞 75%、收藏 42%；4★ 55%/16%；3★ 22%/5%）。
> `foods.like_count` 只由 `likes` 表统计，不再用评分条数顶替，因此「X 人点赞」与
> 「我的点赞状态」始终一致。`seed_comments.py` 的评论作者只能从「给这道菜打过分」的用户里挑，
> 且 4~5★ 写好评、3★ 写中评、1~2★ 写吐槽，评论时间晚于评分时间。

### 3. 配置数据库连接

数据库连接信息在 `config.py` 中，默认值如下，可通过环境变量覆盖：

| 配置项 | 环境变量 | 默认值 |
|--------|----------|--------|
| 主机 | `DB_HOST` | `localhost` |
| 用户名 | `DB_USER` | `root` |
| 密码 | `DB_PASSWORD` | `123456` |
| 数据库名 | `DB_NAME` | `food_db` |

### 4. 安全相关配置（可选）

| 配置项 | 环境变量 | 说明 |

## 推荐算法说明

### 算法设计

| 环节 | 做法 | 原因 |
|------|------|------|
| 相似度 | 共现项去均值后的皮尔逊相关 | 直接对原始评分做余弦，会把「打分宽松」误判成「口味相似」 |
| 相似度收缩 | `sim × n / (n + 6)` | 只共同评过 1 道菜就判高度相似，噪声太大 |
| 预测模型 | `b_ui = μ + b_u + b_i`，协同过滤只拟合残差 | 先解释「用户宽严」和「菜品质量」，避免预测值挤在同一档 |
| 邻域筛选 | 每行只保留 Top-K 相似邻居 | K 值可比，控制噪声传播 |
| 冷启动 | 评分 < 2 条时走热门兜底 | 与业务逻辑一致 |

### 推荐理由怎么来的（可解释性）

排名分数直接给用户看没有意义，但 Item-CF 的分数本身就是可拆解的：

```
score(u, i) = b_ui + Σ_j [ sim(i, j) × (r_uj − b_uj) ] / Σ_j |sim(i, j)|      j ∈ 用户 u 评过分的菜
```

也就是说「哪几道你评过分的菜把这道顶上来」可以逐项追溯。实现上（`utils/cf.py::explain_candidates`）：

1. 取候选菜 `i` 与本用户已评分全部菜品的相似度 `sim(i, j)`，只保留 `> 0.05` 的正相关项；
2. 优先展示用户打了 4 分以上的菜（「你给『客家酿豆腐』打了 4 分」），同类里按相似度排序，最多 2 条；
3. 补一条平台口碑（评分人数 ≥ 5 时才展示，避免「3 个人 5 分」的噪声）；
4. 菜名由路由层补全；已下架/删除的菜品对应理由直接丢弃，不出现悬空引用。

详情页的「相似口味推荐」是同一套相似度矩阵的另一个用法：取该菜的 Top-4 邻居。

### 搜索的同义词扩展

粤菜同物异名多（白斩鸡 / 白切鸡、皮皮虾 / 濑尿虾、馄饨 / 云吞），词表见 `utils/search.py`。
关键词命中任一同义词组就把整组词加入 OR 条件，只补召回、不改排序；页面上会提示
「已按同义词一起检索」，避免用户以为搜错了。

### 首页每日热榜（非个性化）

和 Item-CF 那条 per-user 链路互补：新用户没有行为历史，个性化推荐只能退回兜底；
而「今天大家在吃什么」是全站口径，谁来看都一样。

**热度打分**

```
Hot(f) = 0.48·V̂(f) + 0.30·R̂(f) + 0.13·Ĉ(f) + 0.09·F̂(f)
```

| 分量 | 含义 | 计算 |
|------|------|------|
| `V(f)` | 浏览热度 | `Σ 2^(-Δh/36)`，Δh 为距今小时数，半衰期 36 小时 |
| `R(f)` | 近期口碑 | `(Σscore + μ₀·k) / (n + k) / 5`，取近 7 天评分，`k=3`、`μ₀=3.8` 贝叶斯收缩 |
| `C(f)` | 讨论热度 | 近 7 天评论数的同样衰减和 |
| `F(f)` | 收藏热度 | 近 7 天收藏数的同样衰减和 |

`V̂ / Ĉ / F̂` 各自除以窗口内最大值做归一化（量纲不同，不归一化会互相压制）。

**版式与交互**：榜单内嵌在首页头部右侧——左边是大标题与搜索框，右边是当前第一名的菜品卡片，
两块共用一张轻度虚化压暗的背景照片，看起来是一整个头部而不是两个独立板块。卡片 6.5 秒自动轮播、
悬停暂停；两侧各有一个平时隐藏的箭头，鼠标进入卡片才浮出来（触屏设备常驻）；卡片下方的缩略条
悬停即切换对应菜品，缩略条、卡片、右上角序号三者共用同一索引。搜索或分类筛选时热榜收起，
头部降级为纯搜索版式。

**几个刻意的设计**

- **半衰期 36 小时**：昨天看的算 0.63、三天前算 0.35，不用硬切「今天 0 点」——
  凌晨打开网站时若严格按当天统计，样本会少到排名随机抖动
- **今日加权 ×1.10**：今天有人点开的菜排名略前，避免「上周爆过、这周没人看」的菜一直霸榜
- **贝叶斯收缩**：1 条 5 分的新菜不会直接登顶，票数少就往全站均值 3.8 收
- **口碑门槛**：评价人数 ≥5 且均分 <3.5 的菜直接剔除，再热也不上首页
- **多样性约束**：同一分类最多 2 道、同一商家最多 1 道，避免整屏都是同一家店
- **同一天内稳定**：同分时按浏览量、均分、ID 兜底排序，刷新不会跳来跳去

**PV 从哪来**

每次打开美食详情页写一条 `food_views`（记 `user_id` 或匿名 `visitor_key`），
同一访客 30 分钟内反复刷同一道菜只记一次，防止 F5 把榜单刷歪。
管理员预览和下架菜不计入。`histories` 表继续只服务「我的浏览记录」，
两张表口径不同，互不干扰。

演示数据由 `seed_food_views.py` 按长尾分布生成（点赞多、评分高的菜更常被点开），
`--reset` 可只清掉这批模拟记录。

### 离线评估方法

- **划分**：按用户分层留出法，每个用户随机留出 20% 评分作为测试集（评分 ≥ 5 条的用户才参与）
- **相关性判定**：测试集中评分 ≥ 4 视为「喜欢」
- **Top-N 指标**：Precision@10、Recall@10、NDCG@10、覆盖率
- **回归指标**：MAE、RMSE（预测用户会打几分）
- **对照组**：随机推荐、热门推荐（贝叶斯平均）

### 实验结果（200 模拟用户 / 74 菜品 / 5061 条评分，Top-10，协同过滤取 K=5）

| 策略 | Precision@10 | Recall@10 | NDCG@10 | 覆盖率 |
|------|--------------|-----------|---------|--------|
| 随机推荐 | 0.0649 | 0.2023 | 0.1309 | 1.0000 |
| 热门推荐 | 0.0938 | 0.3080 | 0.1989 | 0.2838 |
| User-CF | 0.1062 | 0.3547 | 0.2241 | 0.8919 |
| **Item-CF** | **0.1201** | **0.3758** | **0.2716** | 1.0000 |

- 两个协同过滤算法均显著优于随机与热门基线，Item-CF 在小样本、物品数适中时表现最好
- 热门推荐覆盖率仅 28%，流量集中在少数菜品；协同过滤有效扩展了长尾曝光
- 评分预测：User-CF 在 K=5 时 MAE = 0.6209，K=20 时降至 0.5490，RMSE 0.7887 → 0.6936
- 数据为可复现的模拟集（`generate_mock_data.py --seed 42`），重新生成后指标会有 ±0.005 的浮动

> 完整对比（含 K=5/10/20/40 与 Top-5/10/20 切换）见管理后台 → 推荐效果评估页。
